### [腾讯开源 DFly2 复用稀疏 KV](https://www.marktechpost.com/2026/11/26/tencent-dfly2-speculative-decoding-sparse-models/) ⭐️ 8.0/10

腾讯开源了 DFly2（代码在 Tencent/AngelSpec）：它是一个 0.85B 参数、5 层的投机解码 drafter，不单独建 KV cache，而是读取目标模型配对稀疏层的 latent KV，只在目标 indexer 已选出的 top-k 位置上计算注意力。它面向 DeepSeek-V4.1-Flash、GLM-5.3-Flash 和腾讯 Hy4 flash 这类原生稀疏模型，drafter 随 Hy4 flash 发布。腾讯称在 DeepSeek-V4.1-Flash 的 SWE 64K、相同单用户速度下吞吐最高提升 81%，但在 Hy4 flash 通用任务 temperature 0 只比 DSpark 高 3.9%；这些是论文和官方数据，尚无第三方复现。

rss · MarkTechPost · 11月27日 03:31

**「怎么用」** 入口是 Hugging Face 的 tencent/Hy4-flash 和 GitHub 的 Tencent/AngelSpec；从 Hy4 flash 仓库取 DFly2 drafter 权重，按该模型的 vLLM recipe 起目标模型，再把 drafter 挂到服务里。论文的测试配置是单实例 TP8、NVIDIA H20，而 recipe 默认给的是 8×H200，换卡型时要重算 TP 和显存。

**「成本与上限」** 论文 Table 2 的对照是：传统 3 层 drafter 每 token 额外占 3.0–3.4 KiB（bf16），相当于目标 KV 的 1.20x–1.76x；32K 下省掉这份 cache，同一显存池可多放 1.73x 请求。收益强依赖目标模型和负载，同一套对比里从 Hy4 flash 通用任务 temperature 0 的 3.9% 到 DeepSeek-V4.1-Flash SWE 64K 的 81%，且只适用于本身有稀疏注意力的目标模型。公开材料没有每百万 token 报价或独立吞吐复现，也没有 H20/H200 之外的硬件数据。

**「为什么现在」** 这不是新的投机解码范式，变化点是 drafter 不再自建 KV cache，而是复用目标模型的稀疏 KV 和索引；对正在用稀疏长上下文模型做高并发服务的人，省下的正是会和并发抢的显存。

### [GPT-6.2 计费纠错](https://www.techmeme.com/261126/p16#a261126p16) ⭐️ 6.0/10

OpenAI 承认 GPT-6.2（Astra 与 Sol 两个型号）在发布时的计费存在错误，用量被错误地打了折扣，现已修正。据 TechRadar 报道，修正是对 Astra 用户生效的：同样的工作量现在会更快触及套餐用量上限，最快提前 40%。受影响的是按套餐配额计费的 ChatGPT 付费用户；报道没有给出旧折扣的具体比例、换算规则，也没有给出新价格或新配额数字，因此无法据此反推每百万 token 的实际成本，API 侧是否同步调整同样未说明。

rss · Techmeme · 11月26日 13:01

**「怎么应对」** 先挑一个代表性任务（一份长文档总结、一次代码重构），在修正后的计费下重跑一遍，量出它实际吃掉多少配额，再把这个数乘以最多 1.4 作为新预算。若工作流本来就贴着限额跑，可以缩短单次请求的上下文、把大任务拆成分批调用，或把非关键调用换成更小的型号，重新分配配额。

**「费用与上限」** 官方没有公布新的每百万 token 单价，这次变化直接体现在订阅计划的用量额度上：Sol 用户触达上限的速度提高 25%，Astra 为 40%（据 Notebookcheck 与 HN 条目）。补偿是一次性用量重置，官方未说明各档计划的具体额度数值、重置周期或速率限制。HN 上有用户称收到措辞含糊的「额度再次下调」邮件，实际扣减规则的可预期性仍然偏低。

**「为什么现在看」** 这里没有新能力：折扣本身是发布期的计费错误，现在是补账，之前基于折扣期算出的成本和配额规划全部偏低。

### [Clay 拆解 GTM Agent 成本](https://latent.space/p/how-clay-builds-gtm-agents-jeff-barg-head-of-ai/) ⭐️ 6.0/10

Clay AI 负责人 Jeff Barg 在访谈中披露了 GTM Agent「Sculptor」的第二次改版：从 2025 年 9 月基于 Sonnet 3.5 时代模型的工具循环（tool loop），改为运行在 Pi harness 上的编码 Agent，在云端沙箱中执行 Clay CLI，并新增 Audiences 数据层，将 CRM 与 Gong 的记录对齐。Clay 自家 Agent 与外部 harness（Claude Code、Codex）的使用量已接近 50/50，Clay 还计划推出一个沙箱 Agent，允许外部 Agent 免费调用 Clay 的工具与构建模块。需要注意，文中提到的 TypeSafe Jev 分类器与自动模型路由都尚未上线，相关数字是 Jeff 的口算估算，并非实测结果。

rss · Latent Space · 11月26日 23:02

**「怎么用上」** 目前可用的入口是 Clay 的 Agent Plugin，提供 CLI 与 API，让 Claude Code 和 Codex 直接操作 Clay 的数据与工作流；Clay 自家的 GTM 团队就在 Cursor 与 Codex 中准备交易资料。想在 Clay UI 内使用，则可直接使用 Sculptor Agent。面向所有外部 Agent 的免费沙箱、TypeSafe Jev 分类器、自动模型路由这三项都尚未发布，访谈中没有给出上线日期。

**「成本与上限」** Jeff 的口算：Clay 库中约有 4000 万家公司，按每家 LinkedIn 页面约 1000 token、ICP 描述再加约 500 token 计算，用一个分类器把全部公司打分一遍约需 1500 美元；而多数客户现在只筛 1 万家左右。他把合格的富化预算定为每条合格线索 1–10 美元、每通预约电话 10–100 美元，并认为线索资格判定已「接近解决」：在 Clay 的评测上，模型约一年来已接近分数上限，过去一年内几乎任何模型都能查出公司最新融资轮。前沿模型的价值集中在深度调研与编排。架构上没有使用 Temporal 或 LangGraph，而是自建 BullMQ 运行 Agent 任务、Postgres 与 ClickHouse 存储产品数据、Snowflake 做分析；按行启动 Agent 会让 5 万行表格一次性占满推理需求，Clay 用 LangSmith 观测并自建了限流与暂停/恢复机制，但 Jeff 不确定 BullMQ 能否撑住再十倍增长。他还给出后训练的门槛判断：推理支出达到 1000 万至 1 亿美元之前，不值得自行训练小模型。

**「实测反馈」** 这是负责人自述，并非第三方评测。Barg 承认 Agent 仍会犯基础错误，比如用相同输入反复重试同一条 CLI 命令；更关键的是 Agent 还无法调试 Agent：让它读取长 trace 并找出失败点，模型往往只标出耗时最长的那一步，而真正的错误在别处，因此 Clay 的不少 skill 仍是手写。正面例子是他问 Agent「有多少 YC 公司用 Clay」，约一分钟拿到答案，一年前这需要抓批次数据、开 Snowflake 权限再手工交叉比对。他也提到 Workflows 刚推出时客户困惑甚至不满、要求还回表格，现在 agency owner 已接受，且多数 workflow 由 CLI 或 Agent 生成。

**「为什么现在看」** 编码 Agent 这条路已经被验证可用，Clay 自己就是从工具循环迁移过来的实际案例；但真正可复用的新东西（TypeSafe Jev 分类器、自动路由、对外开放沙箱）都还在路上，现在读到的更多是工程取舍与成本基准，而不是能立刻照抄的方案。

### [llama.cpp 发布 AMD 基准面板](https://huggingface.co/blog/ggml-org/llamacpp-amd-bench) ⭐️ 6.0/10

llama.cpp 在 Hugging Face 的 ggml-org 博客发布了面向 AMD 平台的基准测试仪表盘，覆盖 Ryzen 处理器与 Radeon 显卡，把在这两类硬件上跑本地推理的实测性能数据集中到一个公开页面。用 AMD 机器跑 llama.cpp 的人可以拿自己的型号去对照。但公告本身没有给出任何 tokens/s、首 token 延迟、显存占用等具体数值，也没有交代测试所用的量化格式、驱动版本、内存带宽配置或可复现步骤，所以目前只能确认这个仪表盘存在，还不能据此推算自己机器上的实际表现。

rss · Hugging Face Blog · 11月26日 11:37

**「怎么用」** 入口是 Hugging Face 上 ggml-org 的这篇博客（huggingface.co/blog/ggml-org/llamacpp-amd-bench），页面内提供仪表盘链接，无需账号或申请。打开后按自己手上的 Ryzen 或 Radeon 型号找相近配置的条目，作为本地跑分是否正常的参考基线。

**「为什么现在看」** llama.cpp 的公开性能数据长期偏向 NVIDIA 与 Apple Silicon，AMD 平台上「我的机器算快还是慢」缺少官方对照口径；但这次只是把已有测试数据整理成入口，不是新能力发布，具体收益要等页面补上型号与参数细节后才能判断。

### [Google 拟让 AI 智能体走 Workspace MCP，Gmail 服务器被指不能发信](https://techstackups.com/articles/google-workspace-ai-agents-mcp/) ⭐️ 7.0/10

据 TechStackUps 报道，Google 计划让 AI 智能体通过 Workspace 的 MCP 服务器访问其产品，其中 Gmail 服务器被描述为不能发送邮件，发送能力仅向合作伙伴开放。报道称该限制源于对“人工确认”的考虑，但社区评论者指出 MCP 已有 elicitation 原语，可在工具调用前暂停并请求用户确认，因此把发送做成合作伙伴专属更像商业决策而非安全需要。另有评论者称 Gmail API 现已支持发送，并质疑文章说法已经过时。由于原始来源无正文、也没有可用的工具结果核实，Google 的完整计划、上线时间和实际限制仍不确定。

hackernews · ritzaco · 11月26日 09:44 · [社区讨论](https://news.ycombinator.com/item?id=50653477)

**「背景」** MCP（Model Context Protocol）是让 AI 代理调用外部工具和服务的接口；Google 的 Workspace MCP 服务器通过 MCP 表单 elicitation，在发送邮件等敏感操作前要求人工确认。Gmail 的 MCP 服务器目前标注为 Developer Preview，属于 Google Workspace 开发者预览计划。

**「影响」** 对依赖 Workspace 集成的智能体开发者而言，如果发送邮件确实被排除在公开 MCP 服务器之外，常见绕行方案是让智能体操作浏览器界面完成发送，这会增加延迟、失败率和维护成本；在 Google 公布正式文档与可用范围前，团队应把“能否通过 MCP 发信”视为未确认项，并准备基于 Gmail API 或人工确认流程的替代路径。

**「社区讨论」** 有评论者认为 MCP 总体上推动了 Google 补齐长期缺失的 Workspace API 能力，例如 Docs API 十多年来无法把评论附着到文本范围、建议模式也不可用；另一些人则争论 Gmail 发送限制的动机，认为若真是为了人工确认，用 MCP elicitation 即可，无需设为合作伙伴专属，并担心用户会转而用浏览器自动化绕过限制。

### [面向 AMD GPU 的 llama.cpp 社区分支引发优化讨论](https://devnull.land/amd-specific-llama-cpp) ⭐️ 7.0/10

Hacker News 上出现一篇介绍 llama.cpp 的 AMD 专用社区分支的文章。由于没有附带正文内容，这个分支相对于上游 llama.cpp 具体改了哪些代码、支持哪些型号、性能提升了多少，都还没有公开的量化数据可以核实。帖子的讨论集中在如何让 llama.cpp 在 AMD 显卡上跑得更快，尤其是 2018 年前后的 gfx906 数据中心卡；这类卡没有张量核心，也不原生支持 bf16。

hackernews · julianlam · 11月26日 17:11 · [社区讨论](https://news.ycombinator.com/item?id=50657265)

**「背景」** llama.cpp 是常用的本地大模型推理引擎；AMD 约 2018 年的 gfx906 数据中心卡（如 MI50、MI60、Radeon VII）拥有 HBM2 高带宽，但缺少张量核心和原生 bf16 支持。此前已有社区分支通过 GCN/HIP 路径专门为这批卡优化 llama.cpp，当前这个 AMD 专用 fork 延续了同类适配工作。

**「影响」** 对使用 gfx906 等老款 AMD 数据中心卡做本地推理的人来说，这类分支的改动点在于针对没有张量核心、不支持原生 bf16 的硬件单独编写内核；评论者指出，把 Nvidia 的内核移植到 ROCm 后，需要对照原实现做数值验证，才能确认移植结果可信。

**「社区讨论」** 评论者 rao-v 称，2025 年初有人注意到 gfx906 系列配备 HBM2 显存，带宽约 1 TB/s、单卡 32GB 显存，二手价格约 200 美元；围绕这类卡优化 llama.cpp 已形成一个小生态，rao-v 也贴出了自己的仓库。fiddlerwoaroof 表示自己在 MI100 上通过激进优化 AMD 代码、并将部分 Nvidia 内核移植到 ROCm，使 Qwen3.8 的性能提升到原来的两到三倍，并称自己用 Claude 把移植内核与原始实现做过数值对照。以上均为评论者的个人说法。
